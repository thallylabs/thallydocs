Usa el hospedaje gestionado de Thally cuando quieras publicar, vistas previas de pull requests, dominios personalizados y reversión desde un solo espacio de trabajo. Autoaloja cuando tu equipo necesite controlar la capa de hospedaje además del repositorio.

## Elige una ruta de despliegue compatible

| Destino | Contrato incluido | Comando o acción de producción |
| --- | --- | --- |
| Thally Cloud | Compilación, vistas previas, versiones, enrutamiento y reversión gestionados | Publica el sitio desde [Thally Cloud](https://app.thally.io/) |
| Vercel | Compilación nativa de Next.js mediante la CLI de Thally | `npx --yes @thallylabs/cli@latest deploy --prod` |
| Cloudflare Workers | Configuración de OpenNext, configuración de Wrangler y scripts del proyecto | `npm run deploy:cloudflare` |
| Docker o un host de contenedores | La receta documentada de imagen de servidor | `docker build -t my-docs .` |

<Warning title="Netlify no es un destino de despliegue compatible">
  Un scaffold sin cambios no tiene `netlify.toml`, adaptador de Netlify ni un contrato probado de directorio de publicación. No ejecutes `netlify deploy --build --prod` contra él. La CLI puede informar de un despliegue activo después de subir la raíz del repositorio, mientras `/` y todas las rutas de documentación devuelven 404. Usa una de las rutas compatibles anteriores o crea y prueba una integración de Next.js específica de Netlify antes de tratar Netlify como destino de producción.
</Warning>

## Publica con Thally Cloud

El [inicio rápido](/es/quickstart) crea o conecta un repositorio de GitHub y publica el sitio en una dirección de `thally.app`. Después de eso, ocurre lo siguiente.

- los pushes a la rama de producción inician una publicación;
- los pull requests de documentación reciben vistas previas aisladas;
- los cambios solo de documentación pueden publicarse más rápido que los cambios de aplicación;
- una publicación fallida deja la versión anterior en línea; y
- la reversión restaura una versión exitosa anterior sin reescribir el historial de Git.

Abre **Deployments** para ver la versión publicada, las vistas previas, el historial con búsqueda, las reparaciones, los redespliegues y la reversión. Consulta [Hospedaje gestionado](/es/guides/managed-hosting) para ver las instrucciones de operación.

Para un despliegue autoalojado, completa las comprobaciones siguientes y elige el proveedor que coincida con tus requisitos operativos.

## Antes de desplegar

1. Define el origen de producción.

   ```bash
   THALLY_SITE_URL=https://docs.example.com
   ```

2. Valida el contenido y la navegación.

   ```bash
   npx --yes @thallylabs/cli@latest check --ci .
   ```

3. Crea una compilación de producción.

   ```bash
   npm run build
   ```

`THALLY_SITE_URL` proporciona enlaces canónicos, metadatos de Open Graph, sitemaps y URL orientadas a agentes. Defínela en el proveedor de alojamiento en lugar de hacer commit en el repositorio.

## Elige el runtime necesario

Usa un despliegue con capacidad de servidor para estas funciones.

- Solicitudes **Try It** de la API;
- chat con IA y rutas MCP remotas;
- el panel de administración y la ingesta de analíticas;
- documentación protegida con contraseña;
- comentarios, búsqueda y otras API de servidor en tiempo de ejecución.

Una exportación totalmente estática solo es adecuada cuando necesitas páginas de documentación renderizadas y assets estáticos. Las funciones anteriores dependen de rutas de servidor y no funcionarán en una compilación con `output: 'export'`.

Track lo gestiona Thally Cloud. Un sitio gestionado no necesita alojar un webhook de Track ni almacenar credenciales de la GitHub App.

## Añade configuración de producción

Solo se requiere `THALLY_SITE_URL` para un sitio público básico. Añade credenciales y variables de almacenamiento solo para las funciones que habilites. Consulta la [referencia completa de variables de entorno](/es/guides/environment-variables).

Para hosts sin servidor, configura almacenamiento libSQL remoto cuando las analíticas, los ajustes, el estado de las tareas o los contadores de límite de velocidad deban sobrevivir a los redespliegues. Un host de Docker o un VPS puede, en cambio, persistir el directorio local `.data/` en un volumen.

## Verifica el sitio publicado

No trates el mensaje de éxito de la CLI de un proveedor como prueba de que el sitio funciona. Para un sitio público, ejecuta solicitudes GET contra la página de inicio, una página anidada real y un endpoint de agente.

```bash
DEPLOY_URL=https://docs.example.com
curl --fail --silent --show-error --location "$DEPLOY_URL/" >/dev/null
curl --fail --silent --show-error --location "$DEPLOY_URL/quickstart" >/dev/null
curl --fail --silent --show-error --location "$DEPLOY_URL/llms.txt" >/dev/null
```

Los tres comandos terminan con estado `0` si tienen éxito y fallan con respuestas HTTP 4xx o 5xx. Sustituye `/quickstart` por una ruta anidada que tu proyecto publique realmente. Para documentación protegida, haz las mismas solicitudes con la autenticación que usan tus lectores y verifica por separado la respuesta sin autenticación.

Después, comprueba lo siguiente.

1. Abre la página de inicio y una página anidada en escritorio y móvil.
2. Sigue los enlaces de la barra lateral, la búsqueda, las migas de pan y los enlaces anterior y siguiente.
3. Comprueba `/sitemap.xml`, `/robots.txt` y `/llms.txt`.
4. Prueba cualquier función de servidor habilitada, incluidos Try It, chat, comentarios, administración o protección de acceso.
5. Confirma que las URL canónicas usan el dominio de producción.

Si el proveedor informa de éxito pero estas solicitudes devuelven 404, inspecciona el registro de compilación y el artefacto subido antes de cambiar las rutas de la aplicación. Un despliegue que subió la raíz del repositorio o trató `.next/` como un directorio estático normal no publicó un artefacto de servidor Thally ejecutable. Sigue el [diagnóstico de todas las rutas 404](/es/guides/troubleshooting#el-proveedor-reporta-éxito-pero-cada-ruta-devuelve-404).
